# AURIONS — First-Release Acceptance Traceability Matrix

- **Status:** Builder reconciliation artifact; specified, not independently reviewed or runtime-validated.
- **Authority:** The proposed First Usable Release Definition supplies PR-01…PR-18. The owner decision register remains authoritative for owner-reserved choices.
- **Purpose:** Trace every first-release acceptance condition to the contracts, owning work packages, scenario evidence and unresolved gates needed to implement and verify it.
- **Boundary:** This matrix does not approve the proposed product definition, authorize implementation, select the first Android action, or settle cloud/mobile history topology.

## 1. Interpretation rules

1. Every PR criterion is a release-level acceptance condition, not a claim that its implementation or test already exists.
2. A referenced command/query/event or schema is a proposed contract until implemented and executed. Registry presence and schema CI do not prove runtime behaviour.
3. The same cognitive-core implementation and versioned contracts are required in cloud and offline-mobile contexts. This does not determine whether their durable cognitive histories are synchronized.
4. A remote planner cannot grant or exercise authority over a mobile-local resource. Authorization is enforced at the affected resource's execution boundary.
5. The first permitted local action and cross-context history-continuity topology remain owner-reserved. The builder must preserve both gates rather than fill them with assumptions.
6. PR-11 proves persistent feedback and later use of experience; it does not alone prove general learning improvement.

## 3. Reconciliation findings

### 3.1 Product acceptance is broader than current CI

Current CI validates schema/fixture structure, governance-document integrity, work-package graph structure, host SQLite DDL/migration smoke execution and Android probe shell syntax. It does not execute PR-01…PR-18. The acceptance IDs above are release obligations, not passing test IDs.

### 3.2 Cloud/mobile topology is a material acceptance dependency

PR-15…PR-18 require two concurrent deployment contexts, shared contracts/core semantics, offline-mobile independence and strict local authorization. They do not alone decide whether durable cognitive history is continuous across contexts. The owner decision record explicitly leaves that question open. If continuity is required, a bounded synchronization subset must be approved and specified; if it is not required, separate histories must be explicitly accepted and disclosed. Shared contracts do not resolve this choice.

### 3.3 Target-platform evidence cannot be substituted by host CI

PR-01, PR-02, PR-07, PR-13, PR-14, PR-16 and PR-17 require target-specific build, runtime, resource, SQLite, lifecycle or permission evidence. The current host CI results are useful preliminary checks only.

### 3.4 Learning claims remain bounded

PR-11 demonstrates persistent experience-dependent feedback. General improvement requires WP-12 controlled evaluation with frozen baselines, held-out tasks, leakage controls, unrelated-task regression checks and repeatable metrics. No first-release criterion may be marked as proof of general learning merely because a memory or belief record was written.

## 4. Builder completion boundary

This matrix closes a missing builder-owned traceability artifact only after its PR-01…PR-18 inventory is checked against the product definition and canonical WP-00…WP-16 roadmap. It does not close runtime implementation, platform evidence, independent review, product approval, owner-reserved topology/action choices, planning exit or implementation authorization.
