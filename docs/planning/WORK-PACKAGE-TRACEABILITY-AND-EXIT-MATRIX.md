# AURIONS — Work-Package Traceability and Exit Matrix

- **Status:** Builder-authored planning reconciliation; IN PROGRESS.
- **Authority:** The owner decision register, product definition and Project Directorship and Team Operating Standard remain authoritative.
- **Canonical sequence:** `docs/planning/CANONICAL-IMPLEMENTATION-ROADMAP.md`.
- **Contract authority:** `docs/planning/IMPLEMENTATION-READY-PLANNING-CONTRACTS.md` and the domain-specific architecture/contract matrices.
- **Boundary:** This matrix clarifies logical ownership and evidence traceability. It does not authorize implementation, select an owner-reserved option, or claim any work package is implemented or accepted.

## 1. How to read this matrix

- **Accountable owner** means the logical AURIONS component responsible for the contract and state transition, not a named individual or permission to bypass the project's role/approval gates.
- **Inputs** are the versioned upstream facts, contracts or evidence a package consumes.
- **Outputs** are the durable state, interfaces or artifacts the package is responsible for producing.
- **Acceptance IDs** identify required executable evidence. An ID in this table is a planned test until its implementation, execution and result are recorded against a revision.
- **Failure/recovery IDs** identify required negative, interruption, replay, reconciliation or rollback evidence. Where a specific ID is not yet allocated, the owning package must add one before implementation readiness.
- **External/owner gates** cannot be satisfied by a builder inference or documentation edit.

## 3. Cross-package invariants

1. A component owns its state and transitions. Other components use its commands, queries or events; they do not write its private persistence tables.
2. Governance and the execution gateway constrain consequential programmatic execution. They are not prerequisites for objective/world understanding, non-device means reasoning, analysis or human-mediated interaction.
3. An affordance hypothesis is not a capability grant; a discovered descriptor is not permission; a plan is not authorization; a provider receipt is not an observed outcome.
4. Cross-store workflows use store-local transactions plus outbox/inbox and durable reconciliation. No distributed ACID transaction is assumed.
5. Unknown, contradictory or stale evidence remains explicit. A missing observation cannot be silently converted into a fact or a negative.
6. Learning acceptance requires a durable, evidence-linked update that changes later relevant behaviour under controlled comparison; memory writes, successful training jobs or training loss alone are insufficient.
7. No-hardcoding regression coverage must include unseen objectives, entities, contexts and non-device/human-mediated means. A closed operation catalogue is not a substitute for discovery or reasoning.
8. A safety, protocol, authorization or persistence invariant may be deterministic. A developer-authored task-to-action/emotion/outcome mapping may not be presented as acquired intelligence.

## 4. Dependency and readiness interpretation

The prerequisite graph is the one in the Canonical Implementation Roadmap. This matrix does not create new dependency edges. A package is not implementation-ready merely because its upstream package has a proposed document. It requires:
- Stable owned interfaces and explicit schema/version compatibility.
- Acceptance and failure/recovery cases with deterministic fixtures.
- Required external platform/provider evidence.
- Completed predecessor gates.
- Explicit owner authorization where required.

WP-14 is not a prerequisite for current first-release PR-01…PR-18 unless the owner adds model-training scope. WP-16 remains later expansion. WP-15 cannot proceed to implementation authorization while its owner-reserved decisions and predecessor evidence gates are unresolved.
