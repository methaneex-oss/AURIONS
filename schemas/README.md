# AURIONS contract schemas

- [`persistence/`](./persistence/README.md): machine-readable proposed SQLite base schemas and additive migrations; host SQLite execution/migration smoke checks passed in CI, while target SQLite and fault/recovery validation remain open.

This directory is the canonical planning source for machine-readable contracts. The initial schema dialect is JSON Schema Draft 2020-12. A pinned Python-host validator (`jsonschema[format]==4.26.0`) and fixture checks are integrated into GitHub Actions. C++ validator equivalence, C++/Python conformance, runtime integration and Android/Termux feasibility remain unverified.

- `message-envelope.v1.schema.json`: common versioned message envelope.
- `command-query-registry.v1.schema.json`: schema for the command/query registry baseline.
- `event-registry.v1.schema.json`: schema for the versioned event inventory and exact payload/fixture bindings.
- `command-query-registry.v1.json`: machine-readable registry for 54 command records (52 mapped and two explicitly deferred device commands) and 29 typed query types. All 54 command records reference the common envelope (52 bind request payload schemas; two are deferred without first-release payload schemas), and all 29 query entries bind the common envelope, input/result schemas and generic payload-shape fixture references; task-control entries additionally bind their known revision, safe-point cancellation, side-effect and emitted-event contracts. Every entry is `design_only_not_dispatchable` or `deferred_by_scope`; unresolved execution semantics are explicit and null never means a default.
- `first-release-command-query-scope.d04.v1.json` and its schema: machine-readable D-04 owner-accepted scope groups; validator enforces exact, disjoint and exhaustive membership against the live command/query registry. Scope acceptance does not grant dispatch.
- `event-registry.v1.json`: 94 event names keyed by event type (so duplicate names cannot be represented) with payload-schema and fixture references; all remain design-only/non-dispatchable; exact command producer bindings are machine-enforced for 52 events, while 42 have no command producer binding and all 94 have proposed consumer and owner-transition specifications; 15 Action Gateway internal triggers and 27 other non-command ingress/internal triggers are now specified; no exact producer-trigger binding remains unresolved, and runtime-handler/event-specific acceptance execution remains open.
- `error-registry.v1.schema.json`: schema for extensible error-code registry entries and their default recovery metadata.
- `error-registry.v1.json`: 35-code, 13-category seed registry; every entry now links to a category-owned handler contract and one schema-shaped fixture, but all entries remain non-dispatchable until runtime handlers and recovery tests exist.
- `error-handler-fixtures.v1.schema.json`: schema for the error-handler contract fixture set.
- `fixtures/error-handler-cases.fixture.json`: one `contractError` payload fixture for each of the 35 seed codes, linked to its handler contract; fixtures validate payload shape only, not runtime recovery.
- `capability-descriptor-body.v1.schema.json`: extensible evidence-backed descriptor body for provider/interface-specific integrations; it is not the universal representation of possible means.
- `world-interaction.v1.schema.json`: initial open-world objective, entity, relationship, situation, evidence, affordance-hypothesis, interaction-proposal and interaction-outcome contracts. These are context-independent, design-only and non-dispatchable; they do not define a closed ontology, task catalogue, platform list or capability registry.
- `fixtures/world-interaction.fixture.json`: positive human-mediated, non-device scenario proving the initial contract can represent a person/resource relationship and an unexecuted interaction proposal without an Android capability descriptor. This is a contract-shape fixture, not a real interaction.
- `domain-payloads.v1.schema.json`: versioned payloads for command/query envelopes and responses, compatibility negotiation, errors, experience, representation, context, evidence, belief, prediction, appraisal, attention, reasoning, memory, knowledge, goals, plans, decisions, capability discovery/knowledge, operation/task lifecycle, outcomes, learning, self-model, evolution, governance, synchronization, artifact lineage, disclosure, retention/deletion, worker protocol, experiment/candidate lifecycle, dataset-source authorization and immutable dataset manifests. Activation and rollback lifecycle events have state-specific definitions. The descriptor record references the separately defined extensible descriptor body schema.
- `fixtures/domain-payloads.fixture.json`: 95 domain, protocol, command and query payload examples, including dataset-source authorization, dataset manifest, activated candidate and rolled-back candidate examples; it is test data, not production memory or real operations.
- `fixtures/message-envelope.fixture.json`: common envelope fixture containing a generic decision event.
- `fixtures/candidate-operation-digests.fixture.json`: canonical RFC 8785 / SHA-256 vectors for exact candidate activation and rollback approval operations; these are deterministic contract fixtures, not authenticated approvals or runtime verification.
- `fixtures/negative/candidate-identity-mismatch.semantic.json`: schema-valid candidate identity with a deliberately incorrect UUIDv5; the validator proves semantic rejection separately from schema-negative controls.
- `fixtures/negative/`: 48 intentionally invalid fixtures covering descriptor authority injection, missing provenance, invalid selected-decision shape, invalid owner identity type, invalid operation risk class, artifact digest, approval risk class, worker identity, sync conflict lineage, disclosure digest, command/query bindings, error side-effect state, task-run revision, provider blind retry, world-entity evidence, dataset rights basis, private-data authorization, dataset source authorization membership, empty dataset manifests, activation/rollback lifecycle evidence, and candidate activation/rollback with a non-passing evaluation status. Capability IDs and provider-defined interface names are data, not closed enums.
- `fixtures/capability-descriptor.fixture.json`: deliberately generic fixture for contract-shape validation only; it is not a real Android capability or product operation.
- `fixtures/decision-recorded.fixture.json`: decision event body fixture; it is not a selected owner decision.
- `fixtures/provider-lifecycle.fixture.json`: neutral validated-provider, typed provider failure and compatibility negotiation examples; these do not validate a production provider.
- `fixtures/provider-lifecycle-enabled.fixture.json`: positive example proving that provider enablement carries separate governance-decision and current platform-permission evidence.
- `../docs/planning/ERROR-HANDLER-CONTRACT-MATRIX.md`: 13 category-level handler contracts and a 35-code mapping. Handler contracts are specified, not implemented or registered.

Rules:
1. Schema validity never implies permission, trust or authorization.
2. Capability descriptors describe observed interfaces; invocation code remains in trusted adapters. They are one evidence source for possible means, not the universal ontology or the boundary of action reasoning.
3. New contexts, actors, resources, relationships and interaction forms must be representable without adding task-specific branches to the cognitive core. New capability providers are only one such extension case.
4. Unknown or unsupported semantics remain unknown; extension fields cannot change authority or policy.
5. Schemas are versioned. Breaking changes require a new major schema version and compatibility tests.
6. The schemas are planning contracts, not runtime dispatch authorization. The last successful exact-head Python-host Draft 2020-12 run (44038596977 on base 3b3537f) validated the preceding corpus only. The D-02 v2/15-SY expansion requires its own automatic exact-head run before it is considered host-validated; C++ validator equivalence, C++/Python conformance and runtime integration remain open.
7. The existing domain fixture set contains 95 positive domain/protocol/command/query payloads; the separate world-interaction fixture adds eleven context-independent contract examples, including objective and relationship revision snapshots. The schema-negative corpus contains 48 intentionally invalid fixtures, plus a separately validated schema-valid candidate-identity mismatch control and two canonical candidate-operation digest vectors. These totals describe files/examples, not full conformance or semantic coverage.
8. The command/query registry is a design traceability baseline, not a runtime dispatch registry. Production registration is prohibited while any entry has unresolved bindings, and the registry does not replace per-handler state, authorization, idempotency, side-effect, event, error, redaction or recovery contracts.
9. The pinned Python `jsonschema[format]==4.26.0` Draft 2020-12 validator and GitHub Actions workflow enforce 10 top-level schema documents, 9 paired registry/fixture checks, the D-04 owner-accepted scope registry, positive/negative payloads, candidate identity/digest/lineage controls and scenario contracts. Exact current PR #2 head `d1212cdb919bebfc977da6a1c14b3beef09388fe` passed all nine automatic workflow steps in [run 44182835494](https://github.com/methaneex-oss/AURIONS/actions/runs/44182835494): 95 positive domain payloads, 48 schema-negative controls, one schema-valid semantic candidate-identity mismatch control, two canonical candidate-operation digest vectors, 35 code-specific recovery assertions, governance integrity, 17 work packages/62 acyclic dependency edges, all 21 ordered SQLite DDL files on host SQLite 3.46.1 with foreign-key/integrity and Memory v10 invariants, and Android probe shell syntax. This is Python-host/host-SQLite structural validation only: C++ validator equivalence, C++/Python conformance, Android/Termux device feasibility, runtime registration/handlers, sync execution, target runtime behaviour and production security remain unverified.

### D-02 selective synchronization field classification

- `sync-field-allowlist.d02.v1.json` defines the exact versioned default, conditional and excluded field-path sets for the eight owner-selected Option B domains. It is a builder proposal, not an export entitlement.
- `sync-classification-policy.d02.v1.json` maps every exact allowlist path to OWNER_PRIVATE, SENSITIVE or SECURITY_RESTRICTED and a proposed-default, conditional-proposal or local-only treatment. It records cross-domain local-only controls, strictest-source classification, no inferred PUBLIC fields and deny/quarantine handling for unclassified or unmapped numeric sensitivity values.
- `sync-classification-policy.d02.v1.schema.json` validates the policy registry. `scripts/validate_schemas.py` cross-checks exact domain, schema-ref and field-path parity between the allowlist and classification policy. The policy deliberately remains `builder_proposal_not_owner_accepted`, `default_action: deny` and `export_enabled: false` until the owner accepts the exact content. This does not authenticate peers, select cryptographic profiles or implement export/receiver enforcement.
